# 個人用筋トレ記録アプリ v1.0 — Codex実装用 統合仕様書

- 仕様ステータス：機能・主要UI・運用方針はユーザー確定。実装方式の推奨は別記。
- 対象：個人用、スマートフォン優先・PCでも操作できるWebアプリ。
- 使用予定：Codex、Supabase（Auth / PostgreSQL / RLS）。既存リポジトリとSupabaseプロジェクトを**引き継ぐ**こと。勝手に作り直さない。
- 最重要原則：①〜④・⑥で確定した既存のv1.0仕様を維持し、⑤追加トレーニング補助は作らない。
- 文書の読み方：「必須」は合意済み仕様、「推奨実装」は要件を満たす設計案であり機能追加を意味しない。「要確認」は勝手に確定してはならない点。

## 0. 対象範囲と除外

**実装対象：** ①トレーニング記録、②メニュー管理、③成長分析、④履歴・カレンダー、⑥InBody、共通UI/認証/同期/JSONエクスポート。

**対象外：** ⑤トレーニング補助機能（休憩タイマー等）、種目の初期プリセット、メニュー複製、曜日ごとの自動メニュー割当、メニューへの重量/回数の事前設定、動画・画像OCRによるInBody取込、InBody API直接連携、JSONバックアップのインポート/復元、複数端末による同一セッションの同時編集への高度な対応。これらを独断で追加しない。

## 1. グローバル画面構成（UI-001〜UI-009）

- **UI-001 必須：** 下部ナビゲーションは4タブ：`記録` / `履歴` / `分析` / `InBody`。独立したホームタブは作らない。起動時の初期画面は記録トップ。
- **UI-002 必須：** トレーニング入力中は専用フルスクリーンとし、4タブの下部ナビゲーションは隠す。
- **UI-003 必須：** トレーニング中に戻る操作をしたら確認なしで記録トップへ戻る。入力中セッションは自動保存して継続。終了扱いにしない。
- **UI-004 必須：** 進行中セッションがある状態でアプリを再起動した場合も記録トップを開き、再開ボタンを表示（全画面の自動復帰はしない）。
- **UI-005 必須：** 進行中セッションがある間、他タブでは小さな「再開」バーを表示。押すとトレーニング全画面へ戻る。新規セッションを同時開始できない。
- **UI-006 必須：** 種目・メニュー選択ボトムシート表示中の戻る操作は、まずそのパネルだけを閉じる。トレーニング全画面は維持。
- **UI-007 必須：** ライト/ダークに両対応し、端末OSのテーマ設定に連動。
- **UI-008 必須：** 一般的な一覧はコンパクト、トレーニング中の入力欄と主要操作は大きく。タップ領域を十分確保し、数値キーボード表示時も入力欄が隠れない。
- **UI-009 必須：** 主要操作（種目追加、メニュー呼出、終了など）はトレーニング画面下部に固定。数値キーボード表示時には邪魔にならないように縮小・退避等を行う。誤タップしにくくする。

### グローバルナビゲーション概念図

```
記録トップ ── 自由開始 ───────────→ トレーニング全画面
    │          メニュー選択・確定 ─────→     │
    │          （選択中止＝作成なし）          ├─ 種目追加・メニュー適用：ボトムシート
    │                                       ├─ 戻る：自動保存して記録トップへ
    ├─ 進行中は「再開」 ────────────────────────┘
    ├─ メニュー管理：カード一覧 → 新規/編集
    └─ 種目管理：検索一覧 → 登録/編集パネル

トレーニング全画面 → 終了確認 → 完了サマリー → 記録トップ/履歴への導線
履歴タブ → 月間カレンダー・選択日の履歴・直近履歴 → 詳細 → 編集
分析タブ → 全体指標・頻度グラフ・種目ランキング → 種目別分析
InBodyタブ → 最新値・推移グラフ・履歴入口 → 測定履歴 → 詳細/編集
```

## 2. ①トレーニング記録（TR-001〜TR-028）

### 2.1 種目とセッション

- **TR-001：** ユーザーがすべての種目を手動登録。標準種目データベースは搭載しない。
- **TR-002：** 種目の記録タイプは `重量＋回数`（kg, 回）、`回数のみ`（回）、`時間のみ`（秒）の3種類。
- **TR-003：** 同時に進行中にできるセッションは1件のみ。1日に終了済みセッションを複数保存できる。
- **TR-004：** `自由に開始`は押した時点でセッションを作成。`メニューから開始`はメニューを選び確定して初めて作成し、選択キャンセル時は作成しない。
- **TR-005：** 開始と終了は明示操作。記録の変更ごとに端末へ自動保存、サーバー同期。画面離脱/ブラウザ再起動から再開可能。
- **TR-006：** 終了までの実施時間は開始日時から終了日時までの経過時間（途中でブラウザを閉じている時間も含む）。日をまたぐ場合、履歴/集計への帰属日は**開始日**。
- **TR-007：** セッション中の種目の並びはアコーディオン。**同時に開く種目は1つ**。
- **TR-008：** すでに追加済みの種目を再選択した場合、同じ種目セクションを重複作成せず、そのセクションに移動して新しいセット行を1つ追加。
- **TR-009：** セッション内の種目追加は画面下から開く検索/選択パネル。新しい種目の登録にも進める。進行中に保存済みメニューをボトムシートから適用できる。
- **TR-010：** セット行は自由に追加/修正/削除可能。実施済みセットを含む種目セクションを削除するときは確認する。セット削除にも確認を表示し、必要なPRを再計算。

### 2.2 セット入力

- **TR-011：** 各セット行は**2段構成**。上段に前回の対応するセットの値、下段に今回の入力欄（kg/回、回のみ、秒のみ）を表示。
- **TR-012：** 前回値とは、当該種目を**実施した最後の終了済みセッション**の、実施済みセットの値。前回セットの1行コピー/全行コピーを提供。
- **TR-013：** 通常の新しい重量＋回数セットでは、重量の初期値に前回セッションの同じセット番号の重量を使い、無ければ直前セットの重量を使う。回数は空欄のまま。
- **TR-014：** 通常手入力セットは必須入力がそろったうえで、入力欄からフォーカスが外れた時またはキーボードの確定操作時に**自動で実施済み**。キー入力途中では実施済み判定やPR更新を発火させない（内容の端末保存は逐次行ってよい）。
- **TR-015：** 前回値から**コピーしたセット**は必須欄が埋まっていても自動実施済みにならない。編集しても同様。明示的に `実施済み` 操作した時だけ実施済みになる。
- **TR-016：** 一度実施済みとなったセットは、必須値がそろっている限り数値変更後も実施済みを維持し、PRを再評価。必須値を空欄にした場合は未実施に戻す。コピー由来でも明示完了後は同じ。
- **TR-017：** 値の制約：重量は0以上・小数可、回数は1以上の整数、時間は1秒以上の整数。空欄＝未入力。負数/非数値/不適切な小数は拒否または入力エラー表示。
- **TR-018：** 実施済みセットだけをトレーニング実績・PR・成長分析の計算に使う。未実施行を誤計上しない。
- **TR-019：** PRはセットの実施済み確定時にその場で判定し、更新したら数秒間の通知を表示。初回の基準記録では「更新PR」通知を出さない。既存PRと同値なら更新扱いにしない。
- **TR-020：** トレーニング中のPR判定は**暫定**。終了済みで同期成功した記録を分析上の確定値として扱う。

### 2.3 終了・再開

- **TR-021：** 終了ボタンを押すとコンパクトな確認ダイアログ。未実施セットが存在する場合は警告し、未実施行を除外して終了できる。
- **TR-022：** 終了確定後のサマリーは `実施時間・実施種目数・実施済みセット数・更新したPR` だけのシンプル型。
- **TR-023：** 実施済みセット0件のセッションも履歴には残せるが、カレンダーの実施日ドットや分析のトレーニング日数・種目頻度に反映しない。
- **TR-024：** オフラインでも端末内で終了確定できる。その時点の終了日時を固定し `終了済み・未同期` として保持。復旧後に自動同期し、二重登録しない。
- **TR-025：** オフライン終了後は履歴で未同期と明示する。**全体分析への正式反映は同期完了後**。
- **TR-026：** 一度終了したセッションの正式な編集・削除は④履歴から、オンライン保存成功を要する。
- **TR-027：** 進行中のセッションがある状態で別の新規セッションは開始不可。未同期でも端末側で終了済みになったものは進行中ではない。
- **TR-028：** 名前は開始日時からデフォルト生成し、あとから履歴編集で任意の名前に変更可能。

## 3. ②メニュー管理（MN-001〜MN-020）

- **MN-001：** 保存するのは `メニュー名`、`種目IDと順序`、各種目の `予定セット数` のみ。重量・回数・曜日は保存しない。
- **MN-002：** 作成方法は `ゼロから作成`、`終了済みトレーニング履歴から作成`。後者は実施済みセットだけから各種目の予定セット数を作る。メニュー複製機能はなし。
- **MN-003：** メニュー一覧は種目名・予定セット数まで表示できるカード型。右上の `新規作成` から作成方法を選ぶ。
- **MN-004：** カードをタップすると閲覧専用画面を挟まず直接編集画面へ。名前・種目・予定セット数を**1画面**で編集。
- **MN-005：** 種目追加は画面下の種目検索・選択パネル。既に登録済みの同一種目は重複行を作らず、既存の行を参照する。
- **MN-006：** 種目の並び替えはドラッグ。予定セット数は1以上の整数。
- **MN-007：** 編集中は端末で下書き自動保存。正式メニューは明示 `保存` を押し、**オンラインで保存が成功したとき**だけ更新。編集中に閉じても正式版を変更しない。
- **MN-008：** 下書きは**メニューごとに独立**して保持。開く際に下書きがあれば `再開` / `破棄` の確認画面を表示。破棄に確認を要し、正式版には影響しない。
- **MN-009：** メニュー名が空、種目0件、予定セット数が1未満なら正式保存不可。新規作成の未保存下書きは残してよい。
- **MN-010：** 保存済みメニューの編集は保存時に上書き。過去に適用したセッション履歴は変更しない。
- **MN-011：** メニュー削除は編集画面最下部のボタンから、確認後に完全削除。対象下書きも削除。過去の記録は削除しない。
- **MN-012：** 保存済みメニューは自由開始後の途中にも適用可能。メニューがセッション内で別グループになることはなく、通常のアコーディオン種目一覧に統合。
- **MN-013：** メニュー適用時、同一種目については `既存セット行数（未実施も含む）` と予定セット数を比較し、足りないセット行だけを追加。再適用しても無駄に増殖させない。
- **MN-014：** 既存種目の順序は維持。新しく加わる種目のみ末尾に追加。トレーニング中の変更から元メニューを自動更新しない。
- **MN-015：** メニューから開始はメニュー**選択確定後**にセッション作成。キャンセルなら作成しない。
- **MN-016：** 登録種目が削除された場合、正式メニューと各下書きから対象種目を除外する。過去セッションは保持。
- **MN-017：** 種目削除により正式メニューが空になったときは、メニュー自体を自動削除せず `要修正・適用不可` と表示。種目追加・保存で復旧。
- **MN-018：** 進行中セッションがある場合でも管理画面を利用可能。ただし同時に別セッションを開始させない。
- **MN-019：** メニュー中の種目名表示は種目マスタの最新名に追従し、過去セッションの名称スナップショットとは別管理。
- **MN-020：** 保存成功・端末下書き保存・未同期は別表示とし、端末への下書き保存を正式保存済みと表示しない。

## 4. 種目マスタ管理（EX-001〜EX-010）

- **EX-001：** 記録タブに `メニュー管理` と `種目管理` の独立ショートカット。
- **EX-002：** 種目管理は検索欄付きコンパクト一覧。登録・編集は画面下の入力パネル。
- **EX-003：** 種目名は空不可。同名登録禁止。比較時は前後の余分な空白を除く。表示名と内部の固定IDを分離する。
- **EX-004：** 種目名変更後、今後の選択肢・保存メニューの表示名には新名称を反映。過去の履歴には当時の名称スナップショットを残す。
- **EX-005：** 名前を変えても同一種目IDの成長分析は連続したデータとして扱う。
- **EX-006：** 種目の記録タイプは**未使用の場合のみ**変更可能。トレーニングで使用済みなら変更禁止。異なるタイプで記録したい場合は別名の新しい種目を登録する。
- **EX-007：** 進行中セッション内で使用中の種目は、そのセッション終了までマスタ削除不可。
- **EX-008：** 種目削除は確認後、今後の選択対象から除外し、保存済みメニュー・下書きからも除外。過去のセッション実績・名称・分析用データは保持。
- **EX-009 推奨実装：** 過去データの参照整合性のため、種目マスタの物理削除ではなく `archived/deleted_at` による論理削除とする。
- **EX-010：** 同一種目が新規登録時に重複しないよう、画面の検証だけでなくDB側でも適切な制約を設定する。

## 5. ③成長分析（AN-001〜AN-025）

### 5.1 全体分析

- **AN-001：** 全体分析トップは `5指標 → トレーニング頻度棒グラフ → 種目別実施頻度ランキング` の順。
- **AN-002：** 指標5種：①トレーニング日数 ②セッション数 ③種目別実施頻度 ④連続目標達成週数 ⑤週間目標達成率。
- **AN-003：** 指標・期間切替（期間依存部分）は `1か月 / 3か月 / 6か月 / 1年 / 全期間`。トレーニング日数・セッション数・種目頻度・頻度グラフ・ランキングに適用。
- **AN-004：** `週間目標達成率` は**今週**、`連続目標達成週数` は**現在**の状態を表示し、分析期間切替で意味を変えない。
- **AN-005：** 1週間は月曜〜日曜、同日に複数セッションがあってもトレーニング日数は1日。セッション数は完了件数。
- **AN-006：** セッションは完了・同期済みかつ実施済みセット1件以上のものを全体分析に反映。進行中、オフライン終了・未同期のセッションは正式反映前。
- **AN-007：** 週間目標日数を変更できるが、適用は**次の月曜日から**。今週の目標は固定。次週適用前に複数回変更したら最後の設定を採用。
- **AN-008：** 各過去週の目標達成判定は、その週に有効だった目標値で計算。達成率は100%を超えてもよい（例：4日/3日＝133%）。未設定時の達成率/連続達成週数は未定義表示。
- **AN-009：** 連続目標達成週数：現在の週ですでに目標達成なら当週を含める。週の途中で未達の場合は前週までの連続を維持し、未達のまま週が終了してから途切れる。
- **AN-010：** 種目別実施頻度は、選択期間内にその種目の実施済みセットを含む完了・同期済みセッション数で集計。ランキングも同じ基準。
- **AN-011：** 全体分析トップには種目検索への入口を設け、ランキングの種目をタップしても種目別分析へ移動できる。

### 5.2 種目別分析

- **AN-012：** 種目別分析は `PR表示 → 成長グラフ` の順。グラフは同時に1指標を表示し、期間は5種類から切替。
- **AN-013：** `重量＋回数`：最大使用重量、**同一重量での最大回数（重量を選択して絞り込む）**、推定1RM。
- **AN-014：** `回数のみ`：1セット最多回数、1セッション合計回数。
- **AN-015：** `時間のみ`：1セット最長時間、1セッション合計時間。
- **AN-016：** 推定1RM：Epley式 `weight_kg * (1 + reps/30)` を2〜10回のセットに適用。1回の場合は実際の重量、11回以上は除外。表示は小数第1位まで。各セッション内の対象セットから最大値をプロット。
- **AN-017：** 各グラフは対象種目を実施した**完了セッションごとに1点**。同日に複数セッションなら別々の点にする。時刻順を維持。
- **AN-018：** 総挙上重量・総実施セット数などを種目別成長の指標として新規追加しない。
- **AN-019：** PR種類は `最大使用重量`、`推定1RM`、`1セット最多回数`、`1セット最長時間` の4種類のみ。タイプに対応するPRだけ表示。
- **AN-020：** PR初回記録は基準値だが更新通知しない。同値タイは更新扱いにしない。トレーニング中は暫定判定、完了・同期後に正式反映。
- **AN-021：** 完了済み履歴の修正/削除が成功したら関連する全指標・グラフ・PRを再計算。過去PRが無くなった場合も整合させる。
- **AN-022：** 未実施セットは集計から除く。0セットセッションは分析に含めない。
- **AN-023：** グラフ0点＝空状態、1点＝点を1つ表示し、存在しないデータを補完しない。
- **AN-024：** 種目名変更後も内部IDで連続集計。マスタから削除された種目についても過去記録と当時の名称が失われない。
- **AN-025：** 暫定/未同期データは正式な全体実績へ二重計上しない。必要に応じて画面に「同期後に反映」と案内。

## 6. ④履歴・カレンダー（HS-001〜HS-016）

- **HS-001：** 履歴タブは `月間カレンダー → 選択日のセッション一覧 → 直近のセッション一覧` の縦並び。初期選択日＝今日。
- **HS-002：** カレンダーの日付下ドットは、終了済みかつ実施済みセット1件以上のセッションが存在する日だけ。1日に複数件でも日付のドットは1つ。開始日基準。
- **HS-003：** 日付タップでその日のセッション一覧を表示。記録なしなら空状態を表示。
- **HS-004：** 右上の検索アイコンから種目名検索を開き、該当種目を実施したセッションを一覧で探せる。
- **HS-005：** 直近履歴のカードは日付・時刻、カスタム名/既定名、種目名、実施種目数、実施済みセット数、PR表示（該当時）を含む。
- **HS-006：** セッション詳細は全種目・全セット行を縦並びで閲覧（アコーディオンにしない）。開始・終了日時、名称、PRを確認できる。
- **HS-007：** 詳細は初期状態で閲覧専用。明示的に編集モードへ入り、保存/キャンセルを提供。
- **HS-008：** 編集ではセッション名、種目、セット、数値を編集可能。保存時はオンラインでの成功を必要とし、成功したときのみ正式反映。キャンセルは変更を破棄。
- **HS-009：** 編集中に未保存変更があり戻ろうとした場合は、破棄の確認ダイアログを出す。
- **HS-010：** セッション削除は確認後に完全削除し、カレンダー、分析、PRなどを再計算。
- **HS-011：** 終了日時は履歴編集モードからオンラインで変更可能。`終了日時 >= 開始日時` を必須とし、実施時間を再計算。
- **HS-012：** セッション名の既定値は開始日時から生成し、任意の名称に変更可能。
- **HS-013：** 過去の種目名はセッション作成時点/記録当時の表示名スナップショットを保持。マスタの名前変更や削除で書き換えない。
- **HS-014：** 終了済み・実施済みセット0件のセッションも履歴には存在する（ドット・分析には反映しない）。
- **HS-015：** オフラインで終了済みのセッションは端末内履歴で確認でき、`未同期` と明示。正式な全体分析へは同期後に反映。
- **HS-016：** 進行中セッションは終了済み履歴と区別し、`再開` 動線を設ける。

## 7. ⑥InBody管理（IB-001〜IB-024）

### 7.1 トップとグラフ

- **IB-001：** InBodyトップは `最新4指標 → 成長グラフ → 測定履歴入口` の順。
- **IB-002：** 4指標は `体重 / 体脂肪率 / 筋肉量 / BMI`。筋肉量と骨格筋量は別指標として混同しない。CSVヘッダーで実際の値とマッピングする。
- **IB-003：** グラフは `体重 / 骨格筋量 / 体脂肪率 / 体脂肪量 / 部位別筋肉量 / InBody点数` の6種類。プルダウンで切替、同時に1グラフ。
- **IB-004：** グラフ期間は `1か月 / 3か月 / 6か月 / 1年 / 全期間`。
- **IB-005：** 部位別筋肉量は `両腕（左右比較） / 両脚（左右比較） / 体幹` を選べ、左右個別値も確認可能。
- **IB-006：** 測定1件につき1点。同日複数件はすべて保持し、測定時刻不明なら時系列の前後関係を勝手に推測しない。欠損指標は点を省略。点タップで日付/値を確認できる。
- **IB-007：** 同日複数測定の場合は、日付が最新のグループのうち**登録順で最新**をトップ初期表示し、同日の別の測定に切替可能。登録順を測定時刻と誤表示しない。
- **IB-008：** 0件/1件時は空表示/単一点表示。架空の点や値を補完しない。

### 7.2 CSVインポート

- **IB-009：** 画面右上にCSV取り込みボタン。ファイル選択→プレビュー・検証・必要な日付修正→正式保存。
- **IB-010：** InBodyエクスポートCSVを読み込み、元データの**44項目すべて**をヘッダーに従って保存する。CSVのUTF-8 BOMに対応。項目名は実際のサンプルCSVから確認し、未検証の列名を推測で固定しない。
- **IB-011：** CSVの `-` と空欄は欠損 `null`。数値 `0` は欠損に変換しない。元CSVの値を保持しつつ、グラフ・計算用の数値は適切に解析する。
- **IB-012：** 元CSVの日付列が指数表記等で信頼できないケースがあるため、`InBody-YYYYMMDD.csv` のファイル名8桁を既定の測定日とし、保存前に必ず確認/修正可能にする。
- **IB-013：** 複数行のCSVを一括取込可能。行ごとに明確な測定日が読み取れる場合は行別に確認/変更できる。各行の検証結果を分けて表示。
- **IB-014：** 同じ正規化済み測定日かつ全44項目が完全一致する場合は重複としてスキップ。同日で値が異なる場合は `追加 / 特定の既存レコードを置換 / スキップ` をユーザーに選ばせる。
- **IB-015：** 失敗行、形式不正、不足列、数値解析エラーを明示し、正常行を誤って失わない。必要な修正をしてから正式保存。
- **IB-016：** 同日で数値が同じ複数回の実測は、日付・44項目が完全に一致する限り自動区別できない。この限界をUI/判定に反映。
- **IB-017：** CSV取り込みはオンラインでの正式保存成功を必要とする。保存前のプレビューを本データに計上しない。

### 7.3 測定履歴

- **IB-018：** 測定履歴は新しい測定日順。カードに日付と4指標を表示。タップで詳細へ。
- **IB-019：** 詳細は44項目すべてを表示。編集モードを明示的に開始し、測定日と全44項目を修正可能、保存/キャンセルを提供。
- **IB-020：** 明示的編集・削除はオンラインの保存成功時のみ確定。保存しないまま戻る場合は変更破棄の確認。
- **IB-021：** 削除は確認後完全削除。変更/削除成功後に最新4指標・各グラフ・履歴一覧を再計算。
- **IB-022：** 最新測定を削除した場合は次に新しい測定をトップに表示。
- **IB-023：** InBodyの測定・編集はトレーニング日数やPRに影響しない。
- **IB-024：** 画像OCR・InBody API直接取込はv1.0では実装しない。

## 8. 保存状態、オフライン、認証（SY-001〜SY-022）

- **SY-001：** Supabase Authの**メールアドレス＋パスワード**でログイン。個人用でも認証/認可は省略しない。
- **SY-002：** Supabaseの公開可能なキー（Publishable key）はクライアントで利用可。ただし**Secret key / service_role はブラウザ・コミット・ログに置かない**。
- **SY-003：** 所有者のみに読み書きを許すRLSポリシーを各テーブルに適用し、データの `user_id` と認証ユーザーIDを関連付ける。権限チェックをUIのみで済ませない。
- **SY-004：** 初期版は**主として1端末で利用**。スマホ/PC両方のレスポンシブ表示には対応するが、同一進行中セッションの複数端末同時更新・競合解決を必要条件にしない。
- **SY-005：** 保存状態は小さなラベルで**常時表示**：`同期済み` / `同期中` / `端末保存済み・未同期` / `端末保存失敗`。端末保存をサーバー同期済みと誤表現しない。
- **SY-006：** 進行中セッションのセット入力は端末に逐次永続保存し、可能なときにサーバー同期。通信断でも入力を続けられる。
- **SY-007：** メニュー下書きは端末保存を維持。正式版の保存はオンライン保存成功を要する。
- **SY-008：** オフライン中もセッションを端末上で終了確定し、終了日時を固定。`終了済み・未同期` として端末内履歴に保持し、回線復旧後に自動同期。
- **SY-009：** 未同期の終了済みセッションは全体分析に**正式反映しない**。同期完了後に反映し、重複集計を防止する。セッション中のPR通知は暫定。
- **SY-010：** 既存の確定済みセッション履歴、InBody、保存済みメニュー等の正式編集/削除は、オンラインで保存成功した場合のみ確定。オフライン操作を成功扱いにしない。
- **SY-011：** 端末への保存失敗時はエラーを可視化し、入力内容を安易に失わないよう画面を維持。成功済みとして扱わない。
- **SY-012：** ブラウザ/アプリの終了、リロード、ネットワーク中断から未同期記録を復元できること。ただしユーザーが端末のサイトデータを消去すると未同期データが失われ得る旨を明示する。
- **SY-013：** セッションIDは作成時に固定の一意IDを発行し、同期再試行でも同IDを使用。DB側で一意制約を設定し、リトライ時の二重登録を禁止する。
- **SY-014：** 同期成功の応答を確認するまで、端末内の未同期データを削除しない。送信中に通信断が起きても安全に再試行できること。
- **SY-015：** 同期処理は冪等性（繰り返し実行しても同じ結果）とデータ整合性を確保する。順序と版数の取り扱いは推奨実装を参照。
- **SY-016：** ユーザーがログアウトする際に未同期データがあれば注意を出す。未同期データは無関係なユーザーへ混入させない。
- **SY-017：** 明示的編集画面（履歴、InBody、種目など）で未保存変更がある状態で戻る場合は、破棄確認。トレーニング中・メニュー下書きの自動保存にはこのルールを適用しない。
- **SY-018：** 削除は対象を明示した確認ダイアログを表示し、処理成功後に一覧や分析に反映。
- **SY-019：** JSON形式の**データ一式エクスポート**をv1.0に実装。対象はユーザーの全種目/メニュー/セット/セッション/目標設定/InBody44項目、その他関連データ。秘密鍵・パスワード・認証トークンは含めない。
- **SY-020：** JSONエクスポートにはスキーマ版・出力日時を付与。同期未完了のデータを含めるかどうかを明確にし、「完全バックアップ」と誤表示しない（下記の要確認事項参照）。
- **SY-021：** JSONからの再インポート、ワンクリック復元、定期自動バックアップは**未採用**。勝手に作らない。
- **SY-022：** サーバー未接続の間、ローカルのみのデータであることを継続表示する。通信復帰検知だけでなく、同期成功応答でステータスを更新する。

### 共通エラー/確認表示

- トレーニング終了：未実施行があれば警告、除外して終了可。
- メニュー/種目/履歴/InBodyの削除：確認後に確定。
- 明示編集画面で保存せず戻る：破棄確認。
- 下書き再開：`下書きを再開 / 下書きを破棄`。破棄は確認。
- 取り込みバリデーション失敗：原因のある行/列を特定。勝手に読み捨てない。

## 10. 推奨データモデル（実装方針。画面仕様を変えないこと）

| 概念 | 推奨テーブル/保存先 | 主な属性・制約 |
|---|---|---|
| 認証 | Supabase Auth | `auth.users.id` をユーザー参照 |
| 種目 | `exercises` | `id`, `user_id`, `name`, `name_normalized`, `record_type`, `archived_at` |
| メニュー | `menus` | `id`, `user_id`, `name`, `needs_fix` 等 |
| メニュー種目 | `menu_items` | `menu_id`, `exercise_id`, `position`, `planned_sets` |
| メニュー下書き | 端末ローカル (`menu_drafts`) | 対象menu IDまたは新規作成draft ID、編集内容、保存時刻。永続保存 |
| セッション | `sessions` | `id`, `user_id`, `name`, `started_at`, `ended_at`, `status` |
| セッション内種目 | `session_exercises` | `id`, `session_id`, `exercise_id`, `exercise_name_snapshot`, `record_type_snapshot`, `position` |
| セット | `workout_sets` | `id`, `session_exercise_id`, `position`, `weight_kg`, `reps`, `duration_seconds`, `is_performed`, コピー由来フラグ |
| 週間目標 | `weekly_goal_schedule` | `user_id`, `effective_monday`, `target_days`。今週は不変、来週から変更 |
| InBody | `inbody_records` | `id`, `user_id`, `measured_on`, `imported_at`, `source_filename`, `raw_fields`（44項目の正確な名称と値）、解析値 |
| 同期キュー | IndexedDB等ローカル | UUID、変更番号、送信状態、最終同期エラー、端末に保存したペイロード |

**技術上の重要条件：**

1. マスタ名称と記録当時の名称スナップショットを分ける。履歴を修正・削除してもPRを正しく再計算する。
2. `セット実施済み` の状態は計算対象を決める重要な事実。コピー由来か手入力かで初回の実施済み判定を分ける。
3. 週間目標は「現在値1つ」ではなく**有効開始日付きの履歴**を残す。
4. 日付計算は利用者の現地タイムゾーンを明示的に扱い、開始日の帰属・月曜週始まり・日をまたぐセッションで破綻しないようにする。日本で使用する想定なら `Asia/Tokyo` を実装上の初期値とする案が妥当（タイムゾーンの最終実装値はアプリの環境に依存）。
5. CSV44項目の正式列マッピングは**実際のInBody CSVサンプルを検査してから**確定。科学的表記の日付列を無条件に信頼しない。
6. RLSポリシーをすべてのユーザーデータテーブルで動作検証する。
7. 認証情報とアプリデータをJSONに混同しない。
8. ローカル保存や同期時の処理は、接続切断・再試行・リロードに耐える設計とする。

## 11. 受け入れテスト（AT-001〜AT-029）

### 記録・メニュー

1. **AT-001：** 手入力の重量・回数がそろい、入力欄を離れると実施済みになる。キー入力途中のPR判定はしない。
2. **AT-002：** 前回セットをコピーして値を変えても、明示完了するまでは実施済みにならない。
3. **AT-003：** コピーセットを明示完了後に重量だけ変更すると、実施済みのままPRを再評価。必須欄を消すと未実施に戻る。
4. **AT-004：** 前回同一種目の同じセット番号→直前セット重量の順で初期値を決め、回数は空欄。
5. **AT-005：** 同じ種目の再選択は1つのセクションにセット追加。種目を重複させない。
6. **AT-006：** メニュー同一種目の予定5セットに対し既存3行（うち未実施1行）がある場合、追加は2行。再適用は0行。
7. **AT-007：** メニュー下書きでアプリを閉じても復元可能。明示保存前の正式メニューは変更なし。
8. **AT-008：** メニューごとに別々の下書きを保持し、再開/破棄を選べる。
9. **AT-009：** 種目名を変更しても過去履歴名は変更せず、成長分析は同一種目に集計。
10. **AT-010：** 記録済み種目の記録タイプ変更禁止。進行中の使用種目削除禁止。
11. **AT-011：** 種目削除で空になったメニューは自動削除されず、要修正/適用不可。
12. **AT-012：** 未実施セットがある状態で終了確認、除外終了ができる。サマリーに時間/種目/セット/PRのみ。

### 履歴・分析

13. **AT-013：** 同日にセッション2件、履歴は2件、カレンダードットは1つ、実施日数は1日、セッション数は2件。
14. **AT-014：** 日をまたいだセッションは開始日へ帰属。終了日時の修正は開始日時以降だけ。
15. **AT-015：** 0セット実施セッションは履歴に残るがドット/分析に入らない。
16. **AT-016：** 週間目標の変更は来週月曜適用、今週固定。過去週の判定は当時の目標で再計算。
17. **AT-017：** 2〜10回はEpley、1回は実重量、11回以上は推定1RM計算から除外。
18. **AT-018：** PR初回は更新通知なし、同値更新なし。履歴削除後はPRが再計算。
19. **AT-019：** 選択期間を変えても「今週の達成率」「現在の連続週数」の意味は変わらない。
20. **AT-020：** 履歴の編集キャンセル・破棄確認が効き、未保存の値は正式データに反映しない。

### InBody

21. **AT-021：** UTF-8 BOMの44列CSVを読め、`-`はnull、数値0は0のまま。
22. **AT-022：** `InBody-20261104.csv` の日付を採用し、保存前に修正可能。指数表記の日付を誤解析しない。
23. **AT-023：** 完全同一行は重複スキップ、同日異値は追加/置換/スキップを選べる。
24. **AT-024：** 同日に2件保存するとトップで切替可能。グラフ上の2点も消さない。
25. **AT-025：** 測定編集・削除後に4指標と6グラフが再計算。InBody変更で筋トレPRは変わらない。

### 保存・セキュリティ

26. **AT-026：** オフライン中にセット入力→端末保存→終了確定→リロード→履歴に「未同期」。復旧後に1件のみ同期され、正式分析へ反映。
27. **AT-027：** 同期応答前に回線断・再送してもセッション・セットが二重登録されない。
28. **AT-028：** 端末保存失敗を同期済みと誤表示しない。過去履歴/InBodyのオンライン保存に失敗した場合は正式データ不変。
29. **AT-029：** 他ユーザーのデータを取得・変更できない（RLS）。JSONエクスポートに認証トークン・パスワード・秘密鍵が含まれない。

## 12. 段階的実装計画（各段階完了時に動作確認）

## 13. 実装前に残る小さな要確認点（勝手に新機能を確定しない）

- **OPEN-01：** 未同期セッションを端末履歴で表示するとき、カレンダードットも暫定表示するか。要件上、未同期終了を履歴に出すことと、分析正式反映を同期後にすることは確定。実装は区別を明示し、一貫性を保つ。
