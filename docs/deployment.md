# 利用開始・公開前の準備（まだ公開しない）

## 前提

Node.js 24系・npmを使用する。ビルド時に必要なのは筋トレ専用Supabaseの公開用URLとPublishable keyのみ。ブラウザからは本人の認証とRLSで8テーブルにアクセスする。Secret key／service_role／DB管理パスワードはアプリに不要。

| 変数 | 用途と取り扱い |
| --- | --- |
| NEXT_PUBLIC_SUPABASE_URL | 筋トレ専用プロジェクトのURL。ビルド時に指定。接続先ホストをコードでも限定している |
| NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY | 同プロジェクトのPublishable key。公開利用を前提としたキー。Secret keyを代入しない |
| MUSCLE_TEST_A_EMAIL / MUSCLE_TEST_A_PASSWORD | 専用Aテストユーザー。開発・テストだけに設定。本番の公開変数へ入れない |
| MUSCLE_TEST_B_EMAIL / MUSCLE_TEST_B_PASSWORD | 専用Bテストユーザー。同上 |
| HTTP_PROXY等・開発用CA | この管理開発環境の通信経路。本番設定へコピーしない |

NEXT_PUBLICの値はビルドに埋め込まれるため、設定を変更したら再ビルドが必要。資格情報の値をREADME・ログ・GitHubに貼らない。環境設定の新規公開、ホスティングへの値の登録、Supabase設定変更はこの作業では行わない。

## 公開前の確認

1. Phase 6の承認済み新RPC `sync_training_session(jsonb,jsonb)` をSQL Editorで適用し、読み取り監査 `db/proposals/phase6-verify.sql` で4 RPCの署名・invoker・固定search_path・PUBLIC/anon実行不可・authenticated実行可を確認する。8テーブルのRLS/FORCE RLSと32ポリシーを確認する。
2. `npm run verify:phase6:sync` と `npm run test:browser` を実行し、新同期を含む実DB回帰を完了する。専用テストデータ残存0件を確認する。
3. 旧版で「同期済み」を確認し、旧版のタブを閉じてから更新する。新旧版で同じ進行中記録を同時編集しない。旧形式の未同期データで最後の確認済みスナップショットが残っていない場合は、サーバー全内容との完全一致だけを確認でき、異なる内容への更新や消失した行の再作成は安全停止して端末入力を保持する。JSONで内容を確認し、無断上書き・削除で解消しない。
4. 公開するドメイン、HTTPS、利用者・メール認証設定、SupabaseのSite URLや許可URL、メール運用、RLS・権限の監査結果を運用者が確認する。個人用アプリで不要な新規登録を許可するかも確認する。本作業では設定を変更しない。
5. ホスト側のCSP・frame制限・Referrer-Policy・nosniff・HSTSなどのレスポンスヘッダーを検討する。Next.jsのインライン処理、Supabase、Service Workerを許す必要があり、未検証の厳格CSPを推測で適用しない。現在の設定がすべての公開セキュリティ要件を満たすとは扱わない。
6. 実機のソフトウェアキーボード・戻る・タッチ操作と、対象にするSafari/Firefoxを確認する。この環境でのChromiumやVisualViewportエミュレーションを実機検証と同一視しない。
7. デプロイするリリースごとに `public/offline-worker.js` のCACHEバージョンを更新する。既存ワーカーは旧タブが閉じるまで待機し、入力を失わせる自動リロードをしない。アプリが将来ユーザー別HTMLをSSRする構成へ変わる場合、公開画面キャッシュの安全性を再レビューする。

## 推奨するデプロイ案

第一候補はNext.js対応のVercel。専用リポジトリを接続し、Node 24、必要な公開用2変数、`npm run build` を設定してプレビューを確認した後、ユーザーの承認で公開する。プレビューの閲覧制限・ドメイン・認証設定は運用側で決める。自動マイグレーションは実行しない。

別案はNode 24のホスト上で以下を実行し、HTTPSリバースプロキシの背後で運用する。実際の公開操作は未実施。

```sh
npm ci
npm run lint
npm run typecheck
npm test
npm run build
npm run start
```

ビルド時の開発依存パッケージを省略しない。テスト用4変数を実行環境へ残す必要はない。`.next` は成果物であり元ソースではない。運用にはソース、ロックファイル、ビルド・配信手順を保存する。

## 利用開始

初回はオンラインでメールアドレス・パスワード認証し、端末保存が利用可能なことを確認する。まず種目を登録し、自由開始またはメニューから記録する。InBodyはCSVプレビューで測定日・原44項目を確認して正式保存する。

オフライン利用の前に「オフライン用画面：準備済み」を確認する。Service Workerは本番ビルド・HTTPS（またはlocalhost）でのみ使用し、画面と同一オリジンのNext.js静的ファイルだけを保存する。Supabase/APIやJSONファイルはキャッシュしない。初回の未取得画面・認証期限・ブラウザによる保存領域削除までは保証しない。

通信断で入力・終了しても「未同期」のまま保持し、復旧後の成功確認で正式反映する。端末保存失敗時は画面を閉じず再試行する。未保存入力の消失を防ぐため、端末保存失敗中のログアウトは止める。

JSON出力はサーバーと端末の別状態を保持する参照用データ。出力日時・取得確認・件数・警告を確認して保管する。オフラインで出力用キャッシュがない場合、サーバー区分は取得不能となり、空データとは扱わない。復元や自動バックアップはできない。

端末のサイトデータ削除は、未同期記録・下書き・オフライン画面を消す可能性がある。本番と開発は別オリジンで使い、開発用サーバーを本番と同じオリジンで起動しない。
