### 履歴（HS-001〜016）

- 月間カレンダー→選択日の記録→直近の記録。今日を初期選択。日付キーは明示した利用者のタイムゾーンで計算し、開始日へ帰属させる。
- 終了済み・実施済みセット1件以上の日だけ点を表示。同日複数件でも点は1個、0セット記録は履歴に残して点・PRに含めない。
- 未同期完了も履歴に表示し、未同期を含む日は輪郭の点として区別する。正式PRの集計対象は同期済み完了のみ。進行中の記録は別表示して再開可能にする。
- 種目名検索は当時のスナップショットと最新マスタのIDの両方で検索でき、検索を閉じると絞り込みを解除する。
- カードは日時・名称・種目・実施種目数／セット数・PR・同期状態を表示。詳細は全種目・全セットを縦に並べ、最初は閲覧専用。
- 明示編集で名称・種目／セット・数値・終了日時を変更。終了日時は開始日時以降。既存種目名・記録タイプのスナップショットはサーバー側でも保持し、新規追加分だけマスタから採用する。
- 未保存編集の戻る・閉じる・再読み込みに破棄確認。未同期完了は正式編集・削除を禁止。オンライン成功応答でだけ正式反映する。
- 親の削除と子の削除は既存の複合外部キーのON DELETE CASCADEにより1 SQL文で確定。履歴の版数も条件にし、古い画面からの削除を成功扱いにしない。
- 編集／削除後は共有workoutsと端末キャッシュを更新し、カレンダー・PRを元データから再計算する。古い端末のPRメタデータも無効化し、Phase 4からも同じ更新済みデータを参照できるようにした。
- 種目・メニュー・履歴はRESTの行数上限で途中まで取得した一覧を正式版と誤認しないようページングする。1001番目の種目を削除済み扱いにしないテストを追加した。

## なぜRPC追加が必要か

Phase 2の進行中記録は、端末の完全な記録を残し、複数HTTPリクエストで順に同期する。この方式は新規進行中記録の基本同期には使えるが、既存の正式メニュー／完了履歴を書き換える途中に通信が切れたとき、正式版が部分更新される可能性がある。クライアントからの補償書き込みも通信断では保証できない。

そのため、承認済みの [`phase3-atomic-writes.sql`](../db/proposals/phase3-atomic-writes.sql) は以下の3関数を追加する。

| RPC | 原子的に行う処理 |
| --- | --- |
| save_training_menu | 正式スナップショットの競合確認、名前・全項目の保存 |
| edit_training_history | 完了／版数確認、全種目・セットと名称・終了日時の編集 |
| archive_training_exercise | 使用中チェック、論理削除とメニュー項目の除外 |

- 全てSECURITY INVOKER、search_path固定、所有者はauth.uid()からのみ取得。既存RLSを適用し、PUBLIC／anonの関数実行権限を除外、authenticatedのみ許可する。
- テーブル・既存RLS・既存関数は変更／削除しない。CREATE OR REPLACEも使用せず、同名の関数が既にある場合は全体を停止する。
- メニューは旧正式版のスナップショット、履歴はrevisionを比較して、古い編集による上書きを拒否する。
- 全体が1トランザクション。後半の行で制約違反が起きても、先に削除・挿入した子行と親の変更がすべてロールバックされる。
- 単一親DELETEで子がカスケード削除されるメニュー／履歴削除には、追加RPCを作らない。

**このSQLは本番未適用。既存テーブル／RLSの変更、本番のテスト記録作成、mainへのマージは行っていない。**

## 追加実DB検証：初回結果と競合応答の修正案（2026-11-04）

専用UUIDを使う実DBテストで、メニュー作成・並び替え、履歴編集、スナップショット保持、種目アーカイブとメニュー項目除外、空メニューの保持、親子のカスケード削除、途中の行の制約違反時の全体ロールバックを確認した。初回は55項目成功・4項目失敗。失敗はA/Bそれぞれの古いメニュースナップショット／古い履歴revisionに対する応答コードで、40001ではHTTP 504 `upstream request timeout`となった。正常系や原子性の試験を競合応答の成功と混同しない。

40001は再試行対象となり得るトランザクション障害用コードであり、業務上の競合応答に使った設計を修正する必要がある。`db/proposals/phase3-conflict-response.sql` は、2関数の競合エラーをPostgRESTのHTTP 409用コードPT409へ置き換える案。テーブル・既存RLS・データは変更せず、署名、invoker、所有者チェック、原子的な更新処理を維持する。修正SQLは未承認・未適用。ユーザーは「DB変更を保留して結果のみ報告」を選択したため、追加のDB変更は行わず、修正案だけを保存する。
