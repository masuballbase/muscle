## 同期SQLの提案（適用待ち）

旧同期処理は複数HTTP書き込みに分かれ、完了済みの同revisionを内容比較なしで成功扱いする箇所があった。応答喪失と他の更新を区別し、途中失敗でも正式記録を壊さないため、`db/proposals/phase6-atomic-sync.sql` に新規RPC `sync_training_session(jsonb,jsonb)` を提案する。

- 1関数だけ追加。テーブル・既存RLS・既存3 RPC・既存データは変更しない。
- SECURITY INVOKER、search_path=pg_catalog、全クエリをauth.uid()で限定。PUBLIC/anonの実行不可、authenticatedのみ実行可。
- 端末が確認済みの基準スナップショット、または応答未確認の送信スナップショットとサーバー内容が一致する場合だけ更新。revisionだけでなく全種目・全セットも照合する。
- 親子の更新は同一トランザクション。制約違反で全体ロールバック。同じ内容の再送は何も増やさず成功として確認可能。
- 完了記録の不一致、基準の不一致、削除済み、版の逆行はPT409で安全停止。40001は使用しない。
- 同一所有者のこのRPC呼び出しをトランザクションロックで直列化する。高度な複数端末編集UIや自動マージは作らない。

ローカルPGliteで、作成・再送・更新・同revision内容競合・古い基準・途中制約違反のロールバックを確認した。本番DBへの適用はユーザー承認とSQL Editorでの実行が必要。この環境にはDB管理接続がないため、自動適用しない。`phase6-verify.sql` は適用後の読み取り専用カタログ監査。

適用リスク：関数追加時のDDLロックやAPIスキーマキャッシュ更新、データ量の大きい同期の処理時間、未更新の旧クライアントとの同時利用。公開前に旧タブを閉じ、旧版の未同期記録を確認する。新RPC未適用時は端末入力を保持し、同期成功とは表示しない。

以降の実装・検証結果は作業後に追記する。mainへのマージ、公開、本番設定の変更は行わない。
