# Phase 6 保存・同期品質、JSON出力、総合テスト

## 基盤と確定事項

Phase 5マージ `ae54b566061bd052024856e93e3e8547a9248a99` を確認し、最新mainから `feat/phase6-quality` を作成。SY-001〜022、AT-026〜029および関連要件を対象にする。

OPEN-02はユーザー承認済み：サーバー保存済み8テーブルと、本人のIndexedDBにある未同期セッション・メニュー下書きを別区分で出力する。同一IDの両状態を保持し、出所・同期状態・最終確認・欠損や未取得の限界を明示する。認証情報は含めず、JSONのインポート・復元・自動バックアップは追加しない。

## 同期SQL（追加承認済み、適用・公開確認待ち）

旧同期処理は複数HTTP書き込みに分かれ、完了済みの同revisionを内容比較なしで成功扱いする箇所があった。応答喪失と他の更新を区別し、途中失敗でも正式記録を壊さないため、`db/proposals/phase6-atomic-sync.sql` に新規RPC `sync_training_session(jsonb,jsonb)` を提案する。

- 1関数だけ追加。テーブル・既存RLS・既存3 RPC・既存データは変更しない。
- SECURITY INVOKER、search_path=pg_catalog、全クエリをauth.uid()で限定。PUBLIC/anonの実行不可、authenticatedのみ実行可。
- 端末が確認済みの基準スナップショット、または応答未確認の送信スナップショットとサーバー内容が一致する場合だけ更新。revisionだけでなく全種目・全セットも照合する。
- 親子の更新は同一トランザクション。制約違反で全体ロールバック。同じ内容の再送は何も増やさず成功として確認可能。
- 完了記録の不一致、基準の不一致、削除済み、版の逆行はPT409で安全停止。40001は使用しない。
- 同一所有者のこのRPC呼び出しをトランザクションロックで直列化する。高度な複数端末編集UIや自動マージは作らない。

ローカルPGliteで、作成・再送・更新・同revision内容競合・古い基準・途中制約違反のロールバックを確認した。追加のユーザー承認は受領済み。SQL Editorでファイル全体を実行し、適用・公開の確認が必要。この環境にはDB管理接続がないため、自動適用しない。`phase6-verify.sql` は適用後の読み取り専用カタログ監査。

適用リスク：関数追加時のDDLロックやAPIスキーマキャッシュ更新、データ量の大きい同期の処理時間、未更新の旧クライアントとの同時利用。公開前に旧タブを閉じ、旧版の未同期記録を確認する。新RPC未適用時は端末入力を保持し、同期成功とは表示しない。

以降に実装・検証結果を記録する。mainへのマージ、公開、本番設定の変更は行わない。


## 保存・同期の改善

- 入力ごとの端末保存を維持し、送信する内容と確認済みの基準・未確認の送信候補をHTTP要求前にIndexedDBへ保存する。成功応答のrevisionを確認するまで未同期のまま保持する。成功後も未同期データを先に消す処理はしない。
- オフライン入力・終了・再読み込みを継続し、通信復旧で同じセッション・種目別記録・セットIDを再送する。遅い読み取りのSDK自動再試行で画面が利用できない状態を避け、明示的な読み取り上限を設ける。navigatorがオフラインの時は端末データで開始する。
- 新RPCの原子的保存・完全一致再送により、応答喪失の前にサーバー確定した場合と、ロールバックした場合の両方を扱う。未確認の古い送信が確定していても、その既知スナップショットから現在の入力へ進められる。
- 同revisionでも内容が違う、確認済み行が消失した、別の基準へ変わった場合はPT409で停止。停止フラグは端末にも保持し、リロード後に黙って自動上書きしない。端末入力はJSONでサーバー版と分けて確認できる。高度な自動マージや競合解消UIは作らない。
- 旧データに最後の確認済みキャッシュがあれば基準を引き継ぐ。基準がない旧未同期データは、サーバー全内容との完全一致の確認だけ可能とし、不一致の更新や消失行の再作成を許可しない。
- 未確認の送信候補は63種類まで保持する。超える場合は捨てずに安全停止する。継続的な応答喪失などで停止した場合は内容の個別確認が必要。
- 端末保存失敗はサーバー同期失敗と区別し、保存失敗中のログアウトを止める。未同期／下書きが残る通常のログアウトは既存の確認を維持する。
- 対応環境ではWeb Locksで同一ユーザーの書き込みを1タブに限定する。後から開いたタブは保存を開始せず待機し、元タブが閉じた後に最新の端末内容で開始する。Web Locks非対応の環境は案内を出し、編集は1タブで行う前提。ブラウザをまたぐ高度な分散ロックや共同編集は追加しない。

## JSON出力

記録・履歴・分析・InBodyの4タブ構成を維持し、アカウント欄に出力入口を追加した。承認済みOPEN-02を実装し、形式は [data-export-format.md](data-export-format.md) に記録する。

サーバー全8テーブルを500行ずつ取得し、本人のuser_idを各行で照合する。端末は同一IndexedDBトランザクションで未同期セッション・下書き・出力用キャッシュを読み、UserStoreとログインユーザーを照合する。出力開始・読み取り中・終了時のアカウント変更は出力中止となり、前アカウントのキャッシュへ黙ってフォールバックしない。

実DBで出力対象外になっていた種目の既存管理列 `used_at` を検出して補完した。現行の全8テーブルの列が除外0になることを実ブラウザ試験で確認する。認証情報を含む未知属性は許可リストで除外し、原44項目が欠けているInBody行は補完せず警告する。

## オフライン画面・UI

本番ビルドには公開画面だけのService Workerを追加した。初回オンラインで4ルートのHTMLと同一オリジンのNext静的ファイルを取得する。Supabase/API・認証・測定値・JSONファイルはHTTPキャッシュしない。新ワーカーで強制リロードせず、旧タブが閉じるまで待つ。開発モードでは登録しない。

端末全体の通信を切ったChromiumで、画面リロード・種目選択・セット入力・終了・再リロード・再接続後の一度だけの同期を試験する。これは「Supabaseだけ通信断」の試験とは分ける。初回の未取得画面や保存領域消去後のオフライン表示までは保証しない。

VisualViewportの高さ・オフセットを使い、キーボード表示中の固定ボタン・ボトムシート位置と入力欄のスクロールを調整する。短い画面でもボタンを44px以上にする。実OSのキーボードではなく、Chromium上で高さ変更をエミュレートした検証である。

開発モードの4タブ・認証・JSON出力を別ポートのスモーク試験で確認する。Next 16.4の認証前に非表示となる記録ページに対するinstant検証は、同梱ドキュメントに従って明示的に対象外とした。画面構成や認証方式は変更しない。開発時のキャッシュ無効化の案内と、本番の静的ビルドは区別する。
