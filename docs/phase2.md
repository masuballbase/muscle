対象：`masuballbase/muscle`、ブランチ `feat/phase2-training`。

## 実装

- 種目：手動登録・検索・編集・論理削除、3記録タイプ、空名・重複名の拒否。使用状況を端末とサーバーの両方で確認し、使用済みタイプ変更・進行中の使用種目削除を禁止。名前のスナップショットと固定IDを分離する。
- 記録トップ：自由開始と再開を排他的に表示。別タブには再開バー。全画面では4タブを隠す。戻る操作ではセッションを終了しない。リロード時は記録トップから再開する。
- セット：1種目だけ展開、前回値と今回入力の2段構成、対応行の重量→直前行重量の順で初期値。回数は空。前回はその種目に実施済みセットがある最後の終了・同期済みセッション。
- 実施済み：手入力は必須値がそろってblur/Enterで確定。入力途中にPR通知しない。コピーは編集しても未実施を維持し、明示操作で確定。その後は通常の実施済みセットと同じ扱い（コピーの明示待ちフラグを解除）。必須欄を空にしたら未実施に戻す。
- 編集・削除：セット追加・確認付き削除、実施済み種目セクションの確認付き削除、同じ種目を追加したら同セクションに1行追加。前回値の1行／全行コピー。種目登録・選択はボトムシート。
- PR：最大使用重量・推定1RM・1セット最多回数・1セット最長時間。Epleyは2〜10回、1回は実重量、11回以上は対象外。実施済みのみを評価。初回基準・同値は通知せず、後続の更新を数秒通知。初回セッション内の更新、実施済み値の修正、削除後の再計算にも対応。トレーニング中は暫定扱い。
- 終了：未実施行数を警告し、除外して終了。終了日時を固定し、実施時間・実施種目数・実施済みセット数・更新PRのサマリーを表示。0セットでも終了できる。
- 履歴タブには、端末に残る終了済み・未同期記録だけを表示する小さな領域を追加した。カレンダー・正式な履歴編集等は未実装。

## 保存と同期

IndexedDBはユーザー別DBを継承し、v1→v2で`cache`ストアを追加する。既存ストア・下書きは削除しない。キャッシュはログアウト時の未同期件数に含めず、同期応答済みセッションも未同期と誤判定しない。

変更時に端末の書き込みトランザクションを直ちに開始し、画面上の入力はメモリにも保持する。端末保存の成功を確認してからサーバー同期する。保存失敗時は失敗表示・再試行を提供し、保存中／保存失敗中のブラウザ終了には注意を出す。ログアウトも端末保存の完了を待ってから未同期確認を行う。

セッション・セクション・セットのUUIDは作成時に固定。`revision`／`syncedRevision`で送信中に増えた編集を区別し、古い応答で新しい入力を消さない。入力は毎回端末へ保存し、サーバー送信は短くまとめる。同時送信を避け、未同期の終了済みセッションを新しい進行中セッションより先に送る。

親セッションをactiveで保存し、子行の追加・更新・削除がすべて成功した後にcompletedを公開する。位置の一意制約に合わせて既存行を一時的な位置へ移し、最終位置を保存する。途中失敗でも端末の完全な記録を残し、同じIDで再試行する。サーバーで同じ版の完了を確認できた再送は二重作成しない。版が違う完了記録は上書きせずエラーにする。

状態は `同期済み`／`同期中`／`端末保存済み・未同期`／`端末保存失敗`を表示し、初期確認中と端末書き込み中も区別する。オンライン復帰・一定間隔・手動操作で再試行する。回線復帰だけで同期済みにはしない。未同期の終了記録は正式分析の対象にせず、サーバーで完了確定したものと区別する。

## DBの再利用・変更

**SupabaseのDB・RLS・権限・インデックス変更は0件。マイグレーションSQLの追加・実行なし。**

Phase 1の認証・所有者RLSを使用。既存の `archived_at`、`sessions.status`（active/completed）、`revision`、`workout_sets.is_copied`、`record_type`、所有者を含む複合外部キーを確認して再利用した。各リポジトリ操作で認証ユーザーを確認し、クエリ・データにuser_idを明示する。

種目マスタは物理削除しない。削除時は保存メニューの関連行を除外し、対応する端末下書きのitemsからも除外する。メニュー自体と過去のセッション・名称・記録タイプは保持する。メニュー下書きのitemsはexercise_idまたはexerciseIdを参照する形で対応し、Phase 3の正式なメニューUIは作っていない。

## 対象外と検証限界

- メニュー作成・適用・正式な下書きUI、履歴のカレンダー・正式編集／削除、分析グラフ、InBody、JSONエクスポートは後続Phase。
- 本Phaseでは同一端末の基本的な保存・再送を実装。複数端末／複数タブで同一記録を同時編集する競合解決、RPC等による親子全体の単一トランザクション、あらゆる中断箇所への障害注入、容量不足時の退避などの高度な同期品質はPhase 6で扱う。
- 非トランザクションのため、同期途中のサーバーにはactive状態の部分データが残り得る。端末の完全な記録を残して再送し、子行が揃う前に正式な完了実績へ公開しない。
- 種目削除の関連メニュー・端末下書き更新も複数処理。通信・端末エラー時はエラーを出し、再試行する。後続Phaseのメニュー保存処理ではこの整合性も総合検証する。
- 実スマートフォンのソフトウェアキーボード、Safari/Firefox、OSによるストレージ削除、複数端末競合は未検証。ブラウザのサイトデータを消去すると未同期データは失われる。

## 再実行と手動確認

```sh
npm run lint

npm test
npm run build
npm run test:browser
npm run verify:phase2:cleanup
```

`test:browser`は**実Supabaseへテストデータを書き込む**。A/Bの既存進行中セッションがある場合は対象テストをスキップし、実データに触れない。テストは同時実行しない。中断後は `/tmp/muscle-phase2-browser-fixtures.json` を消さず、cleanupを実行してから再実行する。アプリの確認は `npm run dev -- --hostname 0.0.0.0` で開始し、登録→開始→入力→コピー→戻る→再読み込み→再開→終了を試す。実データの削除はこの手順に含めない。
